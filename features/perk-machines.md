# Perk machines

## Goal

Machines sell perks like Vigoraid, Load-Up, Hellfire, Saint's Brew, Wandering Spirit, and Off-Hand. A perk is a potion effect with no time limit. The machine sells the potion, and the player drinks it to get the perk. Perks need power by default and are lost when the player goes down.

## Data shape

- **Perk effects** are registered `MobEffect`s (`perk/PerkEffects`). Each is one attribute modifier, so anything else that changes the same attribute stacks with it.
- **A perk** is any effect in the mob effect tag `hellstorm:perks` (`data/hellstorm/tags/mob_effect/perks.json`). A datapack can add its own effects to the tag.
- **Potions.** One per perk effect, `hellstorm:<id>`, giving the effect with `MobEffectInstance.INFINITE_DURATION`.
- **The machine** is a wall-buy (`wall-buys.md`): its block entity holds a `WallBuy.Config`.

```json
{ "item": { "item": "minecraft:potion", "nbt": { "Potion": "hellstorm:vigorade" } },
  "cost": 2500, "repurchase": "deny", "requires_power": true }
```

## Implementation

- **Buying** goes through the wall-buy sale. It refuses without power when `requires_power` is set. It refuses only a potion whose effects the player already has; the perk limit isn't checked here. On success the player gets the potion. Emit `perk_bought`.
- **Drinking** is vanilla. A player in a game who would go past the perk limit is refused when they start drinking, so nothing is used up. Only drinking is limited: splash and lingering potions, and any other source of an effect, may take a player past it.
- **Losing perks.** Going `Downed` removes every beneficial effect. Saint's Brew's solo self-revive is handled in `downs-and-revives.md`.
- **Names.** Effect and potion names are lang keys, so trademarked names can be renamed in a resource pack.

## Config surface

- Per machine: the same settings as a wall-buy (item, cost, repurchase, power).
- `players.perk_limit` (5; 4 until 2026-10-24).
- The `hellstorm:perks` and `hellstorm:self_revive` mob effect tags.

## Assets

- The machine uses your textures. Its green is repainted in memory in the color of what it sells (see As built); no texture files are added.
- The effect icons are your sheet, `textures/gui/perk_icons.png` (64×64, 16×16 cells).

## Depends on

`wall-buys.md`, `economy-and-points.md`, `power-switch.md`, `tacz-bridge.md`, `downs-and-revives.md`.

## Verification

- GameTest: buying a perk potion needs power, charges the cost, and emits `perk_bought`.
- GameTest: drinking Vigoraid gives an endless effect that raises max health and heals; going down takes it.
- GameTest: at the perk limit a new perk can be bought but not drunk, and other sources still add it.
- GameTest: a machine refuses a potion whose effects the player already has.
- GameTest: a machine saved with the old `{ perk, cost }` settings loads as that perk's potion.

## As built

- **Perk cans** (2026-10-22, `perk/PerkCanItem`). `hellstorm:load_up` is a can of Load-Up and `hellstorm:vigoraid` a can of Vigoraid, each with your GeckoLib model (`geo/item/<id>.geo.json`), texture (`textures/item/<id>.png`), and display transforms (`models/item/<id>.json`, parent `builtin/entity`). They're drawn by GeckoLib's own `GeoItemRenderer` (made in `client/PerkCanRenderer`, so the server never loads renderer classes to check the item), not `client/BlockAlignedItemRenderer`: the GeckoLib Blockbench plugin's display preview assumes GeckoLib's lift of 0.51 block, so the display settings you export there look the same in game. (The first build drew them block-aligned, half a block lower than Blockbench showed in every view.) A can is drunk like a potion: the drinking pose and sound for 32 ticks, then Load-Up with no time limit and no particles (the effect icon still shows), and nothing is left (a potion leaves a bottle). It stacks to 1, as potions do. Its tooltip lists the effect the way a potion's does.
- **Saint's Brew can** (2026-10-24). `hellstorm:saints_brew`, a `PerkCanItem` for `PerkEffects.SAINTS_BREW`, with the GeckoLib model, texture and display settings the user made (`geo/item/saints_brew.geo.json`, `textures/item/saints_brew.png`, `models/item/saints_brew.json`, whose particle texture was pointed at the can's own). GameTest `PerkGameTests` drinks one.
- **Drink sizes** (2026-10-29). Every drink is the same height in each view whatever its model, about a vanilla potion's bottle: 13 GUI pixels in the inventory (centred), 6.5/16 of a block on the ground, 12/16 in an item frame, on a wall-buy or a vending machine's shelf, 7/16 in third person, 8.5/16 in first person, 10/16 on the head. Each `models/item/<id>.json` scale is that height over the model's (Vigoraid 13.3 pixels tall, Load-Up 9.3, Wandering Spirit 10.3, the bottles 12.2). Until then they shared one set of scales, so Vigoraid drew 1.66 blocks tall in an item frame and overflowed its inventory slot. The translations the user set are kept, but the item frame one puts the drink's base on the bottom of the item's cube, which the shelves need, and the inventory one centres it. The unused `on_shelf` entries are gone. The shelves draw cans at `CAN_SCALE` (0.425), not the 0.28 other items get, so a can stands about 5 of the machine's pixels tall, as the bottles did before; at 0.28 they were about 3.4 and looked tiny (fixed the same day).
- **Off-Hand and Wandering Spirit cans** (2026-10-28). `hellstorm:off_hand` (Off-Hand) and `hellstorm:jockey_energy` (Wandering Spirit, the `jockey_energy` effect), with the user's models and textures. Off-Hand is the Saint's Brew bottle and takes its display settings; Wandering Spirit is the Load-Up can one pixel taller and takes Load-Up's. Each `models/item/<id>.json` is the other can's with the particle texture pointed at its own. Lore: Off-Hand "Carries a third gun" (dark green), Wandering Spirit "Boosts movement speed" (yellow). Purchase defaults 4000 and 2000, refusing a second can. GameTest `PerkGameTests` drinks both.
- **Hellfire can** (2026-10-28). `hellstorm:hellfire`, the user's model (the same bottle as Saint's Brew and Off-Hand) and texture, with Saint's Brew's display settings. Lore "Boosts fire rate" (gold). Purchase default 2000, `deny`. With it every default perk has a can, so a new vending machine sells a Vigoraid can (see Defaults).
  - **Perk rules.** `Perks.drunk(stack)` is a can's perk or a potion's effects, and the perk limit (`Perks.given`) and "You already have Load-Up" (`Perks.alreadyHas`) read it, so a can counts as its perk everywhere a potion does. To sell it, hold a can, look at the machine, and run `/hs wallbuy set <cost> held`, then `/hs wallbuy repurchase deny`. New machines still sell potions by default.
  - **Color.** `client/PerkCanColors` gives every `PerkCanItem` an item color (layer 0): the stack's `CustomPotionColor` if it has one, otherwise the perk's effect color (Load-Up's #3fae4a, Vigoraid's #d33a2c). The model doesn't use it; it's there so a vending machine selling the can repaints itself as it does for a potion.
  - **Another can** is one line in `PapRegistries` (`new PerkCanItem(props, PerkEffects.<PERK>)`), its three asset files named after the item id, and an `item.hellstorm.<id>` lang entry. The model is found from the item id when the can is first drawn. It can't come from a constructor argument: Forge calls `initializeClient` from `Item`'s constructor, before `PerkCanItem`'s own fields are set. (The first build passed a model-name field and so drew with a null name. That crashed the creative tab, and a can in the hotbar logged a stack trace every frame, which made the game unplayably slow.)
  - GameTest `perkCansAreSoldAndDrunkLikePotionsForTheirPerkWithNoTimeLimit`: a machine sells the Load-Up can, drinking it gives infinite Load-Up and leaves nothing, a second can is refused, and a Vigoraid can gives infinite Vigoraid.
- **Renamed** (2026-10-22): Vigorade is Vigoraid, RE:Load is Load-Up, and Jockey Energy is Wandering Spirit. Only the lang entries changed. The effect and potion ids stay `hellstorm:vigorade`, `hellstorm:reload`, and `hellstorm:jockey_energy`, so saved machines, maps, and datapacks keep working, and the Java names (`PerkEffects.VIGORADE`, ...) are unchanged.

- **Effects** (`perk/PerkEffects`, all `BENEFICIAL`, colors from the old perk JSONs). Each modifier has a fixed UUID.

  | Effect | Attribute | Modifier |
  |---|---|---|
  | `vigorade` | `minecraft:generic.max_health` | +20, `addition` |
  | `reload` | `hellstorm:reload_speed` | +1, `addition` |
  | `hellfire` | `hellstorm:fire_rate` | +0.33, `addition` |
  | `saints_brew` | `hellstorm:revive_speed` | +1, `addition` |
  | `off_hand` | `hellstorm:extra_weapon_slots` | +1, `addition` |
  | `jockey_energy` | `minecraft:generic.movement_speed` | +0.07, `multiply_base` |

  - Gaining max health heals the gain, and losing it clamps health, as vanilla Health Boost does.
  - The amplifier scales the modifier as vanilla does, so a Vigoraid II from a command adds 40.
  - `saints_brew` is also in the `hellstorm:self_revive` tag, which is what gives the solo self-revive.
- **Attributes** (`registry/PapRegistries`). All four are syncable and added to every player.
  - `hellstorm:reload_speed` (base 1, 0.1 to 10) and `hellstorm:revive_speed` (base 1, 0.1 to 10) as before.
  - `hellstorm:fire_rate` (base 1, 0.1 to 10) multiplies a TacZ gun's rounds per minute.
  - `hellstorm:extra_weapon_slots` (base 0, 0 to 9) adds to `players.weapon_slots` (`game/WeaponSlots`).
  - The attributes are built outside their suppliers, because mob effects register before attributes and the effects need them.
- **Potions.** One per effect, so each effect also has splash, lingering, and tipped arrow forms, all named in the lang file (`item.minecraft.potion.effect.vigorade` is "Vigoraid").
- **Effect icons** (2026-10-26). `client/PerkEffectIcon` (`IClientMobEffectExtensions`) draws each perk's icon in the HUD and inventory from your sheet `textures/gui/perk_icons.png`: 16×16 cells read left to right, top to bottom, in the order Vigoraid, Hellfire, Saint's Brew, Off-Hand, Wandering Spirit, Load-Up. Each effect passes its cell to `perk(...)` in `perk/PerkEffects`, and the icon reads it when it draws: Forge's `MobEffect` constructor calls `initializeClient` before the subclass sets its fields, so the first build read 0 and every perk showed Vigoraid. The 16×16 icon sits centred in the 18×18 square where vanilla draws its sprites, and fades with the effect on the HUD as vanilla's do. The sheet lives in `gui/`, not `mob_effect/`, because the game stitches everything in `mob_effect/` into its effect atlas. Until then each icon was a square in the effect's color with the perk's initial.
- **What a perk is** (`perk/Perks`). An effect in `hellstorm:perks`. `Perks.held` lists the ones a player has active, and `players.perk_limit` counts them.
  - `Perks.limitRefusal(held, adding, limit)` refuses a potion whose new perks would take the player past the limit: "You can only hold 4 perks". Perks the player already has and non-perk effects don't count. A potion of two new perks needs room for both.
  - Drinking: `LivingEntityUseItemEvent.Start` is cancelled on the server for a player in a game when the potion would go past the limit, with the usual refusal notice. The client keeps its drinking pose until the player lets go of use, since it doesn't know the limit. Splash and lingering potions and `/effect` aren't checked, on purpose. A machine sells a perk potion at the limit too (it only refuses an effect you already have), since the potion can wait in the inventory.
- **Leftovers** (removed 2026-10-23). A game used to throw away what drinking or eating left behind (a potion's bottle, a stew's bowl). Perks now come in cans, which leave nothing, so a bottle or bowl left by anything else stays, in a game or out of it.
- **Losing buffs.** `Perks.clearBuffs(player)` removes every `BENEFICIAL` effect, perk or not. It runs on going down (`Downs.knockDown`), on dying in a game (`GameHooks.onDeath`), on `/hs game leave`, on logout, and for every player when the game ends (`GameManager.end`). Harmful and neutral effects stay. Removing an effect undoes its attribute modifier, so Off-Hand's slot and Vigoraid's health go with it.
- **Fire rate on TacZ guns** (`tacz/PerkGunEffects`). `AttachmentPropertyEvent` multiplies `ROUNDS_PER_MINUTE` by the holder's `hellstorm:fire_rate`. The event only carries the stack, so the holder is the player (server thread) or the local player (client thread) whose main hand is that exact stack; game players are searched too, since test players aren't in the server's player list. It multiplies what is there, so the upgrader's change stacks.
  - Server: any perk effect with a fire rate modifier re-evaluates the held gun when it is added or removed.
  - Client: TacZ times shots on the client too. `tacz/LocalGunPerks` checks the local player's synced `fire_rate` each client tick and re-evaluates the held gun when it changes. This replaces `PerkSyncPacket`.
- **Reload speed and Load-Up** (`tacz/ReloadTimes`, two mixins in `tacz/mixin`).
  - **Why this seam.** TacZ 1.1.8 has no reload-time property, but every reload asks one method how long ago it started: `ModernKineticGunScriptAPI.getReloadTime()`. That covers the built-in `defaultTickReload` (magazine guns like the AK) and every gun pack's Lua `tick_reload` (shell-by-shell guns like the M870 read `api:getReloadTime()` for each shell and for interruptions). Reloads tick only on the server (`LivingEntityMixin.onTickServerSide`), and the client learns the state through TacZ's synced reload state.
  - **Server.** `ModernKineticGunScriptAPIMixin` scales the answer at `RETURN` by the shooter's `hellstorm:reload_speed`: `elapsed * speed`. Mobs without the attribute reload at normal speed.
  - **Client.** The client only plays the animation. `ObjectAnimationRunnerMixin` (a `client` mixin) speeds up `updateProgress` for animations whose name starts with `reload`, from both `update` and `updateSoundOnly`, so the hands and the sounds keyed to the animation keep pace with the server. Draw, inspect, and shooting animations are untouched.
- **Machine block.** Replaced by the vending machine; see "As built (vending machine)" below. These still hold:
  - **Defaults.** A new machine sells a Vigoraid can for 2500, `repurchase: deny`, `requires_power: true` (`VendingMachineBlock.sells(item, cost)`). It sold a Vigoraid potion until 2026-10-28, when every default perk had a can. A machine saved in the old `{perk, cost}` shape still loads as that perk's potion (`sells(potion, cost)`), since the perk ids aren't the can ids (`vigorade` is the `vigoraid` can).
  - **Old saves.** The machine's codec also reads the old `{ perk, cost }` shape. It becomes the potion with the perk's id at that cost (2500 if none), `deny`, needing power. A perk id with no potion is logged and the machine keeps its default. Saving writes the wall-buy shape.
  - **Prompt.** "Vigoraid [2500]", or "No power" while it needs power and the power is off. Hidden for a potion whose effects the player already has, from the local player's synced effects.
  - **Settings.** The wall-buy screen (titled with the block's name, "Vending Machine"), with a "Needs power" row. `/hs wallbuy ...` works on it too, including `/hs wallbuy power <true|false>`, looking at any of its blocks.
  - **Event.** `GameEvent.PerkBought(player, item, cost)`, Lua `perk_bought` with `player`, `item` (the perk's effect id for a perk can or a potion, such as `hellstorm:vigorade`; the item spec otherwise), and `cost`. It fires when the item is handed over, at the end of the vend. A vending machine doesn't emit `wall_buy`.
- **HUD.** Perks show where every effect does, top right and in the inventory, with the icons from `client/PerkEffectIcon`. The bottom-left list of perk names was removed once that was enough.
- **Removed.** The datapack perks (`perk/PerkDef`, `PerkDefs`, `PerkEffect`, `data/hellstorm/hellstorm/perks/`), the `damage_multiplier` effect, `PlayerState.perks` and `bonusWeaponSlots`, `Game.givePerk` and `takePerks`, `PerkSyncPacket`, `client/ClientPerks`, `/hs perk`, and the perk machine's own settings screen.
- **Tests.**
  - JUnit: `PerksTest` (the limit rule), `WallBuyTest.requiresPowerIsOffUnlessSetAndRoundTrips`, `DownsTest` (solo self-revive through `GameWorld.canSelfRevive`; the fake world loses it on going down), `LuaEventsTest.aPerkPurchaseCarriesTheItemAndCost`, `ReloadAnimationTest`.
  - GameTests in `PerkGameTests`:
    - a new machine sells its Vigoraid only with the power on, for 2500, charged from any of its blocks, refuses a second buy while busy without charging, and hands the can over only once its vend ends, with a `perk_bought` event then and no `wall_buy`
    - placed from its item looking north and aiming left, it is four blocks (foot and head, lower and upper) facing south with the block entity in the lower foot; it isn't placed without room above; removing one block takes all four
    - drinking Vigoraid gives an endless effect, 40 max health, and heals 20, all gone when the game ends
    - going down takes Vigoraid, Off-Hand, and Resistance but not Weakness; dying takes Wandering Spirit
    - at the limit, the machine charges nothing and sells nothing, and drinking a new perk is refused without using the potion; an already-held perk and Swiftness can be drunk
    - a machine refuses Vigoraid to a player who has it, and its action is the denial the prompt hides on
    - Saint's Brew gives self-revive and revive speed 2
    - old `{ perk, cost }` settings load as the potion, with and without a cost, and an unknown perk keeps what was there
    - Hellfire raises the held AK's cached RPM by 1.33 when the effect is added, and the game ending restores it
    - Load-Up, bought and drunk, makes TacZ's own `reload()` and `tickReload` feed an empty AK in three quarters of the time; a plain `multiply_base` reload speed modifier does the same

## As built (vending machine)

- **What changed.** The vending machine replaces the perk machine. It keeps the perk machine's ids (`hellstorm:perk_machine` for the block, item and block entity; `perk_machine` in the map's feature index, as `FeatureKind.VENDING_MACHINE`), so saved maps keep their machines' settings. A perk machine placed before this is a single block: it loads as a vending machine's lower foot with its other three blocks missing, and breaks when a block beside it changes. Break and place those again. Removed: the cabinet block model, `client/PerkMachineColors` (the tint), and the perk machine's front in `client/WallBuyRenderer`.
- **Block** (`feature/VendingMachineBlock`). A `TwoBlockMachine` that adds `HALF` to its state, which makes it two blocks tall as well as two wide: four blocks, the lower foot holding the block entity. It is placed like the crate and the upgrader: facing you, long side across your view, toward the side of the clicked block you aimed at, and only with room above both halves. Using any of its blocks buys. Removing any block takes all four. Each block's shape is a full block except the 4 pixels at the machine's outer ends, which the 24-pixel-wide model doesn't reach. `TwoBlockMachine` gained the tall case for it: `HALF`, the upper blocks in `setPlacedBy`, `place`, `blocks`, `mainPos` and `updateShape`. Commands (`command/Targets`) now find a machine's main block from whichever of its blocks you look at, which also fixes `/hs wallbuy` and `/hs upgrader` looking at a head half.
- **Model.** Your Blockbench model and `use` animation, as `geo/block/vending_machine.geo.json` and `animations/block/vending_machine.animation.json`. Its front is its -z side. Its body is 24 by 32 by 16 pixels with its middle 4 pixels off the seam, so it is moved 4 pixels (`VendingMachineBlock.MODEL_OFFSET`) to center it between its two blocks. `client/BlockModelRenderer` now takes each model's front side instead of the crate's turn-around flag: east for the upgrader, west for the crate (moved back a block, since it is made from the foot toward the head), north for the vending machine.
- **Lit and unlit.** `textures/block/vending_machine.png` is your off texture and `textures/block/vending_machine_on.png` your 45-frame on strip, without its `.mcmeta`: `client/VendingMachineRenderer` picks the frame itself at 15 frames a second from the game time, by moving the model's texture coordinates to that frame, since a texture animation's frame times are whole ticks and can't make 15 a second. The machine is lit while it can sell: in a game that includes it, and with the power on if it needs power. The server works this out every tick and syncs it. When it switches, the lit model fades in over the unlit one (or out) over `FADE_TICKS` (1 second): the unlit model is drawn, then the lit one again on top, see-through by how far the fade has to go.
- **Color.** A machine selling an item with a color of its own is repainted around that color, lit and unlit (`client/VendingMachineSkins`, `client/MachineShades`). The color is the item's color on its first layer (`ItemColors`, tint index 0), so potions, dyed leather, and modded items with an item color all count. An item with none leaves the machine green.
  - **The baseline is the median green.** The texture is painted in six greens (hue 89 to 142, saturation 0.33 to 0.73, brightness 0.47 to 0.90). A pixel counts as green at hue 75 to 155 with saturation 0.25 and brightness 0.3 or more, which leaves out the purple trim, the white, the greys, and the cyan glow. The green is only the basis: the median of those pixels' hue, saturation, and brightness, each taken on its own, is #5AB552, the most-used shade. It is measured from the unlit texture, so a repainted texture keeps working.
  - **Each color is repainted by what it does** (`MachineShades.Role`, changed 2026-10-23). Until then, every color was turned by the same hue angle. The purple-tinted greys then took whatever hue was opposite the new color (teal on red, pink on blue), the cyan lights went lime or magenta, and on red the highlights turned pink and the shadows orange, the reverse of the texture's shading. A color's role is told from its hue, saturation, and brightness, not from a list, so a repainted texture keeps working:
    - **Brand** (the greens, as above). The median becomes the item's color. Saturation and brightness are stretched as before: values below the median scale from 0 up to the item's, and values above from the item's up to 1. Each shade keeps its hue offset, but measured toward or away from blue: on the green, the light shades lean toward yellow and the dark ones toward blue, so on any color the highlights turn warmer and the shadows cooler by the same angle (on red: salmon highlights, crimson shadows; on yellow and orange: orange-brown shadows).
    - **Grey**: the lavenders of the cabin, poster, screen frame, and keypad housing, and the navies of the edges, the right panel, and the unlit glass. On the green they sit 117 to 167 degrees from the median green toward blue, so they read as grey beside it. They keep their saturation, their brightness, and that gap, turned the same way as the brand shades: toward blue from the item's hue, whichever way that is. On red that is down through purple, so red's greys are blue-greys with navy darks, not teal, its opposite. Hellfire, Jockey Energy and Saint's Brew get periwinkle with plum darks, a purple sage green. The Load-Up machine (11 degrees from the median) is turned 11 degrees, the same as its greens. History, all 2026-10-23: first their saturation was cut to 40% (washed out beside the painted purple), then they took the item's own hue with their saturation kept (consistent, but the dark ones read as tinted brand color, not the separate hue they are on the green). Keeping the gap's size but turning it the other way (straight rotation) made red's greys mint and its darks dark green.
    - **White** (saturation 0.13 or less, brightness 0.78 or more) and **light** (any color but the brand's with saturation 0.5 or more, such as the keypad's red, and the cyan glow of the screen strip, the top bar, and the lit glass: hue 170 to 215, brightness 0.85 or more) keep their colors.
    - The Python prototypes that chose this, comparing four ways to treat the greys on six perk colors, were not kept; the rules are all here.
  - **The keypad's lights are left alone.** Its two green pixels and three red ones (the red blinks lighter on the lit strip) keep their colors in every frame: a red or green pixel inside the keypad, x 55 to 62 and y 58 to 62 of each 128-pixel frame (`MachineShades.keypadLight`). The keypad's own purple is repainted with the rest.
  - **Built once per color.** The first machine to show a color builds both textures (the 128 by 5760 lit strip too, worked out per distinct color, not per pixel) as `DynamicTexture`s under `hellstorm:dynamic/`. The 32 most recently used colors are kept. A resource reload drops them all so they are rebuilt from the new textures.
  - JUnit `MachineShadesTest`, on the real texture: the median is #5AB552 and there are six greens; the median becomes each test color exactly (red, blue, grey, white, near black); a red repaint keeps six distinct shades in the same brightness order with none left green; on red the lightest green turns toward orange and the darkest toward crimson; the greys, all over 90 degrees from the green toward blue, are unchanged on the median green, and on red keep that gap (turned down, toward blue from red), their saturation, and their brightness; whites and cyan lights are unchanged on red, blue, yellow, and near black; each of the textures' colors has the role it was painted for; the keypad's lights are the only pixels skipped, five in every frame of the lit strip.
- **Glass.** The window's glass, the root bone `machine`'s own cube, is half see-through in both textures. It is held back and drawn last, see-through, and writes no depth (`client/SeeThrough`): the level draws items after every block entity, so glass that wrote depth hid the stock behind it. The stock is drawn over the glass, so it isn't tinted by it.
- **Stock.** Whatever the machine sells stands on its shelves: three shelves, two spots each over the dark marks on each shelf's front edge, one item per spot at the front, 6 in all, upright, facing out, at 0.28 of a block (a perk can at 0.75 of that, 0.21). The scale is taken from the shelf's top, so the bottom of each item's cube stays on the shelf at any size. (Until 2026-10-23 each spot held three, one behind another, 18 in all, and cans were drawn at the full 0.28.) They are drawn in the `cabin` bone's pose, so they shake with the machine.
- **Buying.** Charged at once, through `Shop` as any wall-buy. The machine then vends for `VEND_TICKS` (32 ticks, until the `use` animation's last movement, the end of the shake 1.58 seconds in; the file runs to 4 seconds, still after that) and hands the item over at its end through the same wall-buy delivery (`WallBuyBlock.sale`). If the buyer can't take it then (their inventory filled up), they're refunded and told why. While vending it refuses others with "The machine is busy". The vend isn't saved: a machine unloaded mid-vend keeps the points. A game ending calls off a vend in progress (`MapReset`).
- **The use animation.** Clients play it when the vend reaches them, and time its sounds from that moment, so they keep time with it: each key's click as it hits bottom (3, 6 and 9 ticks in, at pitches 1.0, 1.12 and 0.94, `feature/VendTiming`). The shake makes no sound.
- **The machine's own clock** (2026-10-24). On the client, the machine counts its own ticks (`clientTicks`) and times the vend, its clicks, the light's fade, the lit strip's frame, and the hum's volume by that, not by the client's game time. The game time follows the server's, so behind a lagging server it jumps, back as well as forward: the clicks could play twice and the shake start over. `VendTiming.pressesDue(heard, tick)` gives the clicks between the last tick played and this one, and the machine never moves `heard` back. `ClientTimingLintTest` fails the build on `getGameTime()` anywhere in `client/`.
